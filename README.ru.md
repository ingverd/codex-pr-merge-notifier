# Codex PR merge notifier

[English](README.md) | [Русский](README.ru.md)

Отправляет подписанное событие о мерже GitHub PR в локальный чат Codex, к которому этот PR прикреплён средствами приложения. Экспериментальный инструмент сообщества, не связанный с OpenAI или ngrok.

`GitHub webhook → HTTPS-туннель → локальный обработчик → соответствующий чат Codex`

## Установка с помощью агента Codex

Чтобы попросить об установке, отправьте ссылку на этот репозиторий в **локальный чат Codex desktop для вашего проекта**:

[https://github.com/ingverd/codex-pr-merge-notifier](https://github.com/ingverd/codex-pr-merge-notifier)

По инструкции ниже агент сможет определить параметры установки из вашего проекта. Копировать отдельное поручение для установки не нужно. Вам всё равно понадобятся аккаунт ngrok, права на управление webhook вашего GitHub-репозитория и необходимые подтверждения Windows/Codex. Агент должен спрашивать только о данных или действиях, которые он не может безопасно получить или выполнить сам.

### Инструкция для агента

Если пользователь прислал этот репозиторий для настройки оповещений о мерже, доведи установку до проверки по шагам для Windows ниже. Если ссылку прислали для ревью или объяснения, выполняй именно этот запрос.

1. **Определи целевой репозиторий до клонирования.** Проверь GitHub remote текущего проекта и существующие настройки уведомителя. Используй `owner/repo` текущего проекта, если целевой репозиторий на GitHub.com однозначен; спрашивай только при отсутствии или неоднозначности цели. Remote клона самого уведомителя не является целевым репозиторием. Не выводи URL remote, содержащие учётные данные. Узнай выделенный пользователю домен ngrok из его панели управления или спроси домен, но не токен.
2. **Проверь совместимость и существующую установку.** Убедись, что используются Windows, локальный чат Codex desktop, Node.js 24+ и действующее подключение к приложению, необходимое для `desktop-client.mjs`. Не придумывай и не сохраняй пути IPC приложения. Перед изменениями проверь существующие службу, обработчик, хук, навык и локальные настройки. Переиспользуй подходящую установку; скрипты намеренно отказываются перезаписывать настройки и заменять существующую службу. Если установки конфликтуют, объясни конфликт и спроси, какую пользователь хочет сохранить, прежде чем что-либо заменять.
3. **Используй готовые скрипты.** Клонируй репозиторий в постоянную папку вне рабочей копии приложения пользователя, изучи скрипты и запусти тесты. Используй официальный подписанный бинарный файл ngrok и последовательно выполни раздел **Установка на Windows**. Зависимости npm не нужны. Для новой установки проверь доступность выбранного порта обработчика и порта 4040 локального API ngrok. Автоматизируй описанные шаги доступными инструментами; не добавляй другой супервизор, задачу по расписанию, реестр маршрутизации или глобальное изменение политики оболочки.
4. **Храни секреты локально.** Запусти `connect-ngrok.ps1` в интерактивном локальном PowerShell, чтобы пользователь ввёл authtoken в скрытый запрос. Попроси пользователя ввести `private/webhook.secret` непосредственно в GitHub, как описано ниже. Никогда не считывай и не выводи ни один из этих секретов в результаты инструментов агента, чат, снимки экрана или логи. При необходимости используй штатные подтверждения UAC и проверку хуков Codex; не обходи их. Если шаг требует ввода пользователя, дай ему одно конкретное локальное действие и продолжи после его выполнения.
5. **Проверь работающую установку.** Считай состояние службы ngrok и убедись, что она работает, запускается автоматически, использует учётную запись Local Service и штатные настройки восстановления. Проверь, что выделенный HTTPS-адрес ведёт к настроенному обработчику на `127.0.0.1`, установленный хук старта включён, указывает на эту установку и прошёл необходимую проверку Codex, а `merge-notifier.mjs check` возвращает `connected: true`. Проверь реальные настройки webhook в GitHub: точный целевой репозиторий, `/github/merge`, JSON, включённая проверка SSL и только события `pull_request`. Подтверди, что настоящий ping от GitHub получает HTTP 202. Перед повторением изменения с неопределённым результатом проверь, что фактически произошло.
6. **Проверь маршрутизацию, если есть настоящий PR.** Используй штатное прикрепление PR в предназначенном для него чате Codex, затем запусти `merge-notifier.mjs resolve <PR URL>`. Результат должен содержать ровно этот один подходящий чат. Не прикрепляй все PR к чату установки и не создавай и не мержи PR только для теста. Если подходящего PR нет, сообщи, что маршрутизация не проверена. Ping подтверждает получение webhook и проверку подписи; доставку в целевой чат может подтвердить только настоящий мердж, одобренный владельцем.
7. **Сообщи результат.** Укажи путь установки, настроенный `owner/repo`, URL webhook, пройденные проверки, непроверенные этапы или конкретный блокер, а также команды `$merge-notifier status` / `$merge-notifier reconnect`. Не заявляй о полной проверке всей цепочки, пока не наблюдалось настоящее уведомление о мерже. Сохрани текущие настройки модели и уровня рассуждений чата.

## Возможности и совместимость

- Одна установка работает с одним явно настроенным репозиторием GitHub.com. Этот же код можно использовать со своим репозиторием, доменом и учётными данными.
- Скрипты установки предназначены для Windows, Node.js 24 или новее и локальных чатов Codex desktop. Маршрутизация в облачные и удалённые чаты и установка на других ОС не поддерживаются.
- Для маршрутизации читаются метаданные прикреплённых PR из штатной базы SQLite Codex без её изменения. PR должен соответствовать ровно одному доступному неархивному чату; при отсутствии или неоднозначности маршрута сообщение не отправляется.
- Обработчик использует внутреннюю схему базы установленного приложения и встроенный канал app-tools. Это **внутренние интерфейсы**, а не стабильный публичный API интеграции. После обновлений Codex подключение нужно проверять заново. Исходная интеграция проверялась на Codex desktop 26.930.2377.0 и CLI 0.159.0-alpha.12.1.
- Каждый webhook требует подписи HMAC SHA-256. Отправить сообщение может только событие закрытия `pull_request` с признаком мержа из разрешённого репозитория. Заголовки и описания PR никогда не копируются в запросы к агенту.
- Защита от повторной доставки действует в пределах одного процесса обработчика. Очереди для работы офлайн, постоянного журнала событий и автоматической повторной отправки при неопределённом результате нет.
- ngrok использует штатную службу Windows и механизм восстановления после сбоев. Обработчик переподключается при запуске или возобновлении чата; если он перестал работать между этими событиями, воспользуйтесь командой в чате. При поступлении события Windows и Codex должны работать.

## Установка на Windows

1. Клонируйте этот репозиторий в постоянную папку. Не перемещайте её: определения службы и хука используют абсолютный путь к ней.
2. Скачайте подписанный агент для Windows с сайта [ngrok](https://ngrok.com/download/windows) и поместите `ngrok.exe` в эту папку. Создайте аккаунт ngrok и получите выделенный ему HTTPS-домен. Агент ngrok — отдельная зависимость поставщика, которая не распространяется вместе с этим проектом.
3. В PowerShell из этой папки создайте локальные настройки:

   ```powershell
   .\configure.ps1 -Repository 'your-owner/your-repo' -NgrokDomain 'your-assigned-domain.ngrok-free.dev'
   .\connect-ngrok.ps1
   ```

   Замените значения `your-owner/your-repo` и `your-assigned-domain.ngrok-free.dev` на свой репозиторий и выделенный домен. Вводите authtoken ngrok только в скрытый локальный запрос. `configure.ps1` создаёт отдельный случайный секрет GitHub webhook в `private/`, задаёт права доступа Windows ACL и отказывается перезаписывать существующую установку. Если порт 8028 занят, используйте `-Port 9042`.

4. Откройте PowerShell от имени администратора в папке установки и запустите `install-ngrok-service.ps1`. Скрипт не заменяет существующие службы и процессы ngrok. Служба работает от имени Windows Local Service с автоматическим запуском и штатным восстановлением после сбоев. Она получает доступ на чтение к учётным данным ngrok, но не к секрету GitHub webhook.
5. Из локального чата Codex desktop запустите `install-codex-hook.ps1`. Он добавляет один пользовательский хук `SessionStart` и устанавливает навык `merge-notifier`. Другие хуки сохраняются; существующий навык не заменяется. Если приложение требует проверки хука, просмотрите его и подтвердите доверие через штатный механизм Codex. [Документация по хукам Codex](https://learn.chatgpt.com/docs/hooks).
6. В **Settings → Webhooks** GitHub-репозитория настройте `https://YOUR_DOMAIN/github/merge`, подставив выделенный домен вместо `YOUR_DOMAIN`, формат JSON, включённую проверку SSL и только события `pull_request`. Через локальный редактор введите содержимое `private/webhook.secret` непосредственно в поле Secret в GitHub; не вставляйте его в чат. Запустите обработчик и подтвердите, что ping от GitHub получает HTTP 202.
7. Прикрепите PR к предназначенному для него локальному чату Codex. Интеграция отправляет сообщение, только если это прикрепление есть ровно у одного подходящего чата. Отдельный реестр маршрутизации не нужен.

Работающему обработчику не нужен токен доступа GitHub. Для управления webhook используются ваши обычные права в репозитории. Учётные данные ngrok и webhook хранятся в локальных настройках, исключены из Git и никогда не входят в состав репозитория.

## Команды

В локальном чате Codex:

```text
$merge-notifier reconnect
$merge-notifier status
```

Ручной запуск обработчика из оболочки этого чата:

```powershell
.\start-notifier.ps1
.\start-notifier.ps1 -Reconnect
```

`reconnect` меняет подключение обработчика к приложению. Получатели по-прежнему определяются по прикреплённым PR; команда не направляет все уведомления в вызвавший её чат. Она проверяет принадлежность процесса и никогда не заменяет посторонний процесс, слушающий порт. Перед повторением запуска или отправки с неопределённым результатом нужно проверить, что фактически произошло.

Диагностика без изменений:

```powershell
& $env:CODEX_MCP_NODE_PATH .\merge-notifier.mjs check
& $env:CODEX_MCP_NODE_PATH .\merge-notifier.mjs resolve 'https://github.com/your-owner/your-repo/pull/123'
```

Для прямого запуска `serve` также нужна переменная `MERGE_NOTIFIER_REPOSITORY`; при необходимости используется `MERGE_NOTIFIER_PORT`. `start-notifier.ps1` читает эти настройки из исключённого из Git файла `notifier.json`. Для диагностики можно переопределить путь к штатной базе через `MERGE_NOTIFIER_CODEX_STATE_DB`; иначе файл `state_5.sqlite` ищется в каталоге Codex, определяемом `CODEX_HOME`.

Обработчик пишет сообщения запуска, коды обработки событий и ошибки без секретных данных в `receiver.stdout.log` и `receiver.stderr.log` в каталоге установки, в том числе при прямом запуске `serve`. Скрипт Windows запускает отдельный скрытый процесс без перенаправления каналов хука, поэтому работающий обработчик не задерживает завершение хука.

## Проверка и конфиденциальность

```powershell
npm test
# Или используйте встроенный runtime из локального чата Codex desktop:
& $env:CODEX_MCP_NODE_PATH --test
```

Тесты используют вымышленные репозитории, чаты, события мержа и базы данных. Они не записывают данные в GitHub и не отправляют сообщения в чаты. В публикуемые исходники не включены учётные данные, бинарные файлы, штатные базы, логи, настоящие идентификаторы чатов, личные пути файловой системы и исходные настройки репозитория и домена. Тесты покрывают доставку с подписью и без неё, маршрутизацию, повторную доставку, неопределённый результат отправки и безопасное переподключение. CI запускает те же тесты на Windows.

Тесты исходного кода не доказывают совместимость внутренних интерфейсов будущих версий Codex. После установки или обновления проверьте действующее подключение к приложению, штатную маршрутизацию и ping от GitHub. Успешный ping подтверждает получение события и проверку подписи; для проверки всей цепочки используйте настоящий мердж, одобренный владельцем.
